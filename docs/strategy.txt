# PROCESS NOTES (standing practices - apply to every phase as it's built, not
# just phase 3; revisit/refine as we learn more)
# ---
# - fields come in different flavors: CLASSIFICATION (pick from a small
#   bounded set, lower risk), CONSTRUCTION (invent a structure from scratch,
#   e.g. a thematic axis - higher risk of dressing genre convention up as
#   forced inference), SCALAR-WITH-DOWNSTREAM-CONSTRAINT (a number/range a
#   later phase's math depends on, e.g. endings count). construction and
#   scalar-with-constraint fields need harder adversarial testing than
#   classification fields do - identify which flavor a new field is before
#   drafting it.
#     - flavor call for the new fields below: 3-0a (recurring decision
#       taxonomy) is CONSTRUCTION - treat with the same rigor as
#       core_thematic_axis. 3-0b (who "you" is) is mostly CLASSIFICATION;
#       its epistemic-state sub-field leans CONSTRUCTION. 3-0c (failure
#       model) is CLASSIFICATION at the top level (does a failure state
#       exist: yes/no/soft) but CONSTRUCTION in its specifics - flag for
#       hard testing rather than assuming the top-level simplicity carries
#       through.
# - default posture for sibling fields within a phase: run extraction BLIND to
#   each other unless a specific contamination or dependency risk is
#   identified and documented for that pair (3b/3c: blind, to stop
#   transgression from inflating valence). whatever blind execution misses
#   across a phase's fields should get caught by that phase's own cross-check
#   step (see 3h).
#     - THE CHAIN RULE (resolved, was an open question): chain only when a
#       field is UNDEFINED without the other's output. Never chain for
#       agreement. 3f consumes 3d because setting footprint is not
#       well-defined without the required-excursion list - a dependency.
#       3g now consumes 3-0a and 3-0c for the same reason: branching
#       density and tracked state are not well-defined without knowing what
#       the player decides and what counts as failure. 3-0a/b/c were
#       considered as a chained frame for all of 3b-3g and rejected: the
#       argument for that was CONSISTENCY, and consistency is 3h's job.
#       Blind execution is what makes disagreement legible - on kernel12
#       one field flagged the kernel's own contradiction and another
#       didn't, and that disagreement is the signal 3h needs. A chained
#       run would have hidden it.
# - GENERATION AND VERIFICATION NEVER SHARE A PROMPT. A phase that builds
#   something and checks its own work will talk itself past its own correct
#   objection - observed in-trace at field scale, and it gets worse at
#   structure scale. Split every build/check pair into separate calls with
#   separate JSON, make the checker a CLASSIFICATION task (it lists
#   violations against a fixed checklist and fixes nothing), and make repair
#   a third call that receives the violation list. This costs calls, not
#   design time, and it's the discipline already used between phase 3's
#   fields and 3h.
# - ANYTHING THAT RUNS PER-NODE NEEDS A FIXED INPUT PACKET, defined before
#   the phases upstream of it produce material that won't fit in one. See
#   the node packet note under step 14.
# - confirm a field's actual downstream consumer by rereading that later
#   phase's own wording before finalizing the field's shape - don't assume a
#   plausible-sounding consumer exists just because the shape seems to fit.
# - the kernel (as filtered/adapted by 2a) persists and stays directly
#   available to any later phase that needs specific texture or detail beyond
#   what phase 3 distills. phase 3 intuits the core structural concepts we
#   need to nail down before we can think about casting, structure, setting,
#   etc - it's a distillation for early decisions, not a replacement for the
#   source text.
# - before sinking real design time into an unbuilt phase, run a crude,
#   stubbed-out pass of the WHOLE pipeline (3 through 17) on one simple,
#   low-complexity kernel, even with placeholder logic for phases not yet
#   designed. goal is confirming info actually flows end-to-end the way we
#   think it does, not producing a good story - cheaper to find a broken seam
#   this way than after several more phases are individually polished.
#     - this stub pass should now specifically confirm that a 3-0c failure
#       model, once it exists, actually reaches step 14 (quick exits/bad
#       ends) and step 16 (transition states) - those are currently the
#       only two places anything failure-shaped is mentioned, and both
#       predate 3-0c existing.

# 1) identify what our core assumptions are for the product
#    (interactive, second person, audience)
# 2*) get a kernel from the user
#    (a blurb containing as much information as the user wants to give
#     regarding the desired story)
#   a) filter kernel to required levels wrt audience
#      (this filtered kernel is the version that persists downstream - see
#      process notes above)
# 3) analyze the (filtered) kernel to intuit the core structural concepts we
#    need to nail down before we can think about casting, structure, setting
#
#   [BUILT. These describe the INTERACTIVE CONTRACT: what kind of thing the
#    reader is actually doing, as distinct from what the story is about.
#    Layer-forward was chosen over retrofit; 3d was the one targeted
#    retrofit (third_party_pov excursion type + interactivity flag).]
#
#   0a) the interactive question - what is the reader doing, not what is
#       happening to the protagonist. what decision(s) recur across the
#       story; is there one dominant repeated decision-type (e.g. "who to
#       trust," "what to sacrifice") or several unrelated ones. this is the
#       same mechanical-over-literary framing that reshaped 3d - apply that
#       lesson here first, deliberately, rather than rediscovering it.
#   0b) resolve "you" - who the reader is (may already be partly covered by
#       3d's viewpoint work, but that's about IDENTITY persistence; this is
#       about EPISTEMIC state) - what the reader-as-protagonist knows at
#       story start vs. what's withheld, and whether that gap is itself
#       part of the design (mystery/reveal-driven) or incidental.
#   0c) consequence and failure model - does this story have a distinct
#       failure/"game over" state at all, as opposed to pure branching
#       narrative with no failure concept? if yes: roughly how failure is
#       recognized and what it costs. currently the ONLY places failure is
#       mentioned anywhere in this pipeline are step 14 ("quick exits/bad
#       ends," per-node) and step 16 ("transition states next node or
#       branch") - both far downstream and node-local. deciding this at the
#       top level avoids re-deciding it piecemeal, inconsistently, at every
#       node in step 14.
#
#   a) [FOLDED INTO 3g - do not build separately] rough minimal and maximal
#      length. It had no consumer: 3g(i)'s ending-count range and 3g(ii)'s

#   b) affect extraction (primary, primary trajectory, secondaries, tone, somatic address, transgression level)

#   e) rough timeline requirements/bounds (single time, linear, multiple times, clustered, ...)

#   f) rough setting requirements/bounds (single overall setting, multiple clustered, multiple dispersed)

#   h) [BUILT - build this BEFORE any further phase-3 fields; it is the

#      (the interactive question), 3-0c (failure model), 3g (complexity),
